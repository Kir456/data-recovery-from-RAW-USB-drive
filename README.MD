# TurboRAW Carving Recovery v2.0

**TurboRAW Carver** — универсальная утилита для восстановления удалённых и повреждённых файлов напрямую с физических носителей (RAW Data Recovery / File Carving) в среде Windows.

Программа работает в обход файловой системы (FAT32, exFAT, NTFS) через Win32 API (`\\.\PhysicalDrive`), используя продвинутые алгоритмы анализа внутренней структуры файлов и многоуровневую защиту от ложных срабатываний.

## Что это и зачем

Если ваша флешка, SD-карта или жёсткий диск стал «RAW» (Windows предлагает отформатировать) или файлы были случайно удалены — эта программа попробует их восстановить. Она сканирует весь накопитель байт за байтом и вытаскивает найденные файлы.

## Какие файлы можно восстановить

| Тип | Форматы |
| :--- | :--- |
| 🎬 Видео | MP4, MOV, AVI, MKV, WebM, FLV, WMV |
| 🎵 Аудио | WAV, MP3, FLAC, OGG, MIDI, M4A |
| 🖼️ Фото | JPEG, PNG, GIF, WebP, TIFF, PSD, HEIC |
| 📄 Документы | PDF, DOC/XLS/PPT, RTF, ZIP (DOCX/XLSX/PPTX) |
| 📦 Архивы | RAR, 7z, GZip, XZ, BZip2 |
| 🗄️ Прочее | SQLite-базы данных |

## Что нужно перед запуском

1. **Windows 10 / 11** (64-bit).
2. Скомпилировать программу (см. раздел «Сборка проекта» ниже).
3. **Не записывайте ничего на повреждённый носитель!** Каждая запись уменьшает шансы на восстановление.

## Как пользоваться (по шагам)

1. Подключите повреждённую флешку / диск к компьютеру.
2. Откройте **Командную строку от имени Администратора** (Win+X → «Terminal (Администратор)» или «Командная строка (Администратор)»).
3. Перейдите в папку с программой и запустите:
   ```cmd
   cd C:\path\to\recovery
   recovery.exe
   ```
4. Программа покажет список дисков — выберите нужный по номеру:
   ```
   [*] Обнаруженные диски:
       [0] Samsung SSD 970 EVO (465.76 GB) [NVMe]
       [1] Kingston DataTraveler (14.91 GB) [USB] [Removable]

   Введите номер диска для сканирования: 1
   ```
5. Укажите папку для сохранения восстановленных файлов (или нажмите Enter для текущей папки).
6. Дождитесь завершения сканирования. Следите за прогресс-баром.

## Что важно знать

- ⚠️ **Программа только читает** данные с восстанавливаемого диска. Она ничего не записывает на него.
- ⚠️ **Всегда сохраняйте файлы на другой диск**, не на тот, с которого восстанавливаете.
- Восстановленные файлы получают автоматические имена: `IMG_001.jpg`, `VID_002.mp4`, `AUD_003.mp3`, `DOC_004.pdf`, `ARC_005.rar` и т.д.
- Для фотографий JPEG с данными EXIF имя будет содержать дату съёмки: `IMG_20240315_142530_001.jpg`.
- Файлы DOCX, XLSX, PPTX восстанавливаются как `.zip` — просто переименуйте расширение обратно.
- Если видео восстановилось двумя частями (из-за фрагментации на диске), их можно склеить через FFmpeg (см. ниже).

## Склейка фрагментированных видео (FFmpeg)

Если длинное видео восстановилось в виде двух файлов:

1. Создайте файл `list.txt`:
   ```text
   file 'VID_001.mp4'
   file 'VID_003.mp4'
   ```
2. Выполните:
   ```cmd
   ffmpeg -f concat -safe 0 -i list.txt -c copy Full_Movie.mp4
   ```

## Архитектура и алгоритмы

### 1. Секторное сканирование (512-byte Aligned Search)

В отличие от побайтового поиска, утилита учитывает архитектуру файловых систем: начало любого файла на накопителе всегда выровнено по границе сектора (кратно 512 байтам). Это даёт **ускорение поиска сигнатур в ~512 раз** по сравнению с наивным побайтовым перебором.

```
  Диск:  [сектор 0][сектор 1][сектор 2][сектор 3]...
  Поиск:  ↑ check   ↑ check   ↑ check   ↑ check    (шаг 512)
  Наивный: ↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑...   (шаг 1)
```

### 2. Многоуровневая система распознавания (Multi-Level Signature Matching)

Каждая сигнатура проходит до **трёх уровней проверки**:

| Уровень | Механизм | Пример |
| :---: | :--- | :--- |
| L1 | **Primary Signature** — 4-байтовый magic number с опциональной маской | `FF D8 FF E1` (JPEG EXIF) |
| L2 | **Secondary Signature** — проверка дополнительных 4 байт по смещению | RIFF + `AVI ` (offset 8), ASF GUID bytes 4-7 |
| L3 | **Structural Validation** — анализ структуры заголовка | ID3: synchsafe int, OGG: version=0, MIDI: header_length=6, PSD: version=1 |

Трёхуровневая проверка критически важна для форматов, разделяющих первичную сигнатуру:
- `RIFF` (0x46464952) → **AVI** / **WAV** / **WebP** (различаются по L2: sub-type на offset 8)
- `ftyp` (0x70797466) → **MP4** / **HEIC** / **M4A** (различаются по L2: brand на offset 8)
- Маска `0x00FFFFFF` — для форматов с 3-байтовой фиксированной частью: **GZip** (`1F 8B 08`), **BZip2** (`42 5A 68`)

### 3. «Бронированный режим» (Structure-Aware Carving)

Для контейнерных форматов с парсируемой структурой утилита вычисляет **точный размер файла** и извлекает его целиком, игнорируя сигнатуры внутри потока:

| Формат | Парсер | Метод определения размера |
| :--- | :--- | :--- |
| MP4 / MOV / HEIC / M4A | `ParseMp4Size` | Обход дерева атомов ISOBMFF, поддержка 64-bit extended size (`size == 1`) |
| AVI / WAV / WebP | `ParseRiffSize` | Чтение поля `size` из RIFF-заголовка (offset 4, uint32 LE) + 8 |

Это защищает многогигабайтные видеофайлы от случайного усечения: сжатый видеопоток (H.264/H.265) содержит произвольные байтовые паттерны, которые могут совпасть с сигнатурами других форматов.

### 4. Blade-обрезка (Next-Signature Carving)

Для форматов без парсируемой структуры (MP3, FLAC, OGG, RAR, 7z и др.) утилита использует **blade-алгоритм**: при извлечении файла параллельно сканирует поток на появление «чужой» сигнатуры. Обнаружение начала следующего файла = конец текущего.

**Защита контейнеров от ложной обрезки:** при извлечении ZIP/PDF/DOC/RTF сигнатуры встроенных изображений (JPG, PNG, GIF) и вложенных документов (PDF, ZIP) игнорируются, предотвращая разрыв архива из-за встроенных иллюстраций.

### 5. Trailer Carving (поиск маркера конца файла)

Для форматов с фиксированным маркером завершения файл обрезается точно по трейлеру:

| Формат | Маркер конца | Детали |
| :--- | :--- | :--- |
| PDF | `%%EOF` | Последнее вхождение (PDF может содержать несколько инкрементальных обновлений) |
| ZIP | `PK\x05\x06` + comment_length | EOCD record с учётом поля comment length (2 байта, offset 20) |
| PNG | `00 00 00 00 49 45 4E 44 AE 42 60 82` | Чанк IEND (12 байт, фиксированный CRC) |
| JPEG | `FF D9` | EOI-маркер, последнее вхождение |
| GIF | `0x3B` | Trailer byte |

### 6. Аппаратная совместимость (4K Alignment)

Функция `ReadDiskSafe` автоматически выравнивает все запросы к физическому диску кратно **4096 байтам** (Advanced Format). Буфер аллоцируется через `VirtualAlloc` (страничное выравнивание), что исключает ошибки `ERROR_SECTOR_NOT_FOUND` / `ERROR_INVALID_PARAMETER` при raw-чтении.

### 7. Турбо-буферизация (USB 3.0 / NVMe Optimized)

- Чтение блоками по **32 МБ** (`CHUNK_SIZE`)
- Флаг `FILE_FLAG_SEQUENTIAL_SCAN` включает агрессивное системное упреждающее чтение (Read-Ahead Caching)
- Запись восстановленных файлов через `VirtualAlloc`-буфер (32 МБ)

### 8. Автоматическая идентификация дисков

Через `IOCTL_STORAGE_QUERY_PROPERTY` (`StorageDeviceProperty`) программа получает:
- Модель накопителя (Vendor + Product ID)
- Тип шины (USB, SATA, NVMe, SD, MMC и др.)
- Флаг съёмного носителя (RemovableMedia)

### 9. Интеллектуальная генерация имён файлов

- Префикс по категории: `IMG_`, `VID_`, `AUD_`, `DOC_`, `ARC_`, `DB_`
- Для JPEG с EXIF: парсинг APP1-сегмента → извлечение `DateTimeOriginal` → `IMG_YYYYMMDD_HHMMSS_NNN.jpg`
- Парсер EXIF корректно обходит сегменты APP0/APP1, останавливается на маркере SOS (`0xDA`)

## Ограничения и known issues

| Ограничение | Причина | Обходной путь |
| :--- | :--- | :--- |
| Оригинальные имена файлов не восстанавливаются | Имена хранятся в файловой системе (MFT/FAT), а не в теле файла | Для JPEG — дата из EXIF. Для остальных — категорийные имена |
| Фрагментированные файлы восстанавливаются частично | File carving не знает таблицу кластеров | Склейка через FFmpeg (для видео) |
| DOCX/XLSX/PPTX сохраняются как .zip | Технически это ZIP-архивы с XML-содержимым | Переименовать расширение |
| MP3 без ID3-тега не обнаруживается | Frame sync (`FF FB`) даёт слишком много false positives | — |
| BMP не поддерживается | Сигнатура `BM` (2 байта) слишком короткая для надёжного детекта | — |

## Сборка проекта (Компиляция)

Проект полностью автономен — один файл `main.c`, нулевые зависимости.

### Вариант 1: Microsoft Visual Studio (MSVC)

Откройте **x64 Native Tools Command Prompt for VS** или **Developer Command Prompt** и выполните:

```cmd
cd C:\path\to\recovery
cl /utf-8 /O2 main.c /Fe:recovery.exe
```

> Флаг `/utf-8` обязателен — исходник содержит кириллицу в строковых литералах.

### Вариант 2: MinGW / GCC / w64devkit

```bash
cd /path/to/recovery
gcc -O2 main.c -o recovery.exe
```

## Лицензия и отказ от ответственности

Утилита предназначена исключительно для восстановления собственных данных и проведения цифровой криминалистики (Digital Forensics). Программа выполняет **только чтение** с целевого накопителя и не модифицирует его содержимое. Авторы не несут ответственности за возможную потерю данных при некорректном использовании.
